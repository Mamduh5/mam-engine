## Findings

### DOG-001 — Installed help does not expose action syntax

- Interface: CLI / documentation
- Severity: medium
- Observed: `mam --help` lists groups only; `mam movement --help` is rejected as an unknown command. The packaged README was required as a fallback.
- Expected: installed help should reveal the exact supported movement actions, required arguments, and flags, or direct the user to a working help command.
- Reproduction: run the two help commands above from the temporary consumer workspace.
- Evidence: top-level output ended at the group list; group-level output was `CLI_ARGUMENT_INVALID`.
- Proposed direction: make installed help sufficient for command discovery and make invalid-command errors identify the relevant help path.
- Blocks final `v0.1.0`: yes; the CLI is the authoritative automation interface.

### DOG-002 — Runtime availability check depends on consumer cwd content

- Interface: runtime / package
- Severity: high
- Observed: from the consumer workspace, `mam runtime check --json` failed with `MOVEMENT_FILE_NOT_FOUND` for `examples/movement/default.json`. From the installed package root it passed and found compatible Godot.
- Expected: runtime availability checking should not require an example at a repository-relative path in the consumer workspace.
- Reproduction: install the tarball, change to a workspace containing only `movement.json`, and run the command above.
- Evidence: failed envelope named the missing path; package-root probe reported Godot 4.7 and successful headless smoke.
- Proposed direction: make runtime-check assets independent of the caller's working directory.
- Blocks final `v0.1.0`: yes.

### DOG-003 — Installed runtime proof cannot resolve packaged Godot project from a consumer workspace

- Interface: runtime / package
- Severity: high
- Observed: the installed runtime-test accepted and validated `movement.json` but returned `RUNTIME_PROJECT_NOT_FOUND`. The same installed binary passed from its package root with the packaged example.
- Expected: packaged runtime commands should resolve packaged Godot assets independently of the consumer workspace while treating the workspace as the definition boundary.
- Reproduction: run the two runtime-test commands recorded above from their respective working directories.
- Evidence: consumer-workspace failure versus package-root comparison pass with 120 physics steps and exact metric agreement.
- Proposed direction: resolve runtime project assets from the installed package location rather than the caller's cwd.
- Blocks final `v0.1.0`: yes.

### DOG-004 — Packaged editor start documentation uses the repository command

- Interface: documentation
- Severity: low
- Observed: the packaged README's editor snippet says `npm run mam -- editor serve`, while the preceding paragraph says installed consumers use `mam` directly.
- Expected: installed-use documentation should show the installed executable for the primary editor command.
- Reproduction: read the packaged README `Commands` section.
- Evidence: both statements occur consecutively in the installed artifact.
- Proposed direction: distinguish repository-development and installed-package examples explicitly.
- Blocks final `v0.1.0`: no by itself.

### DOG-005 — No CLI shutdown action for the installed editor

- Interface: editor
- Severity: low
- Observed: startup and HTTP behavior were clear, but automated shutdown required terminating the operating-system process tree. Shutdown completed with no lingering health endpoint.
- Expected: the documented limitation is accurate, but a self-hosting workflow benefits from an explicit clean shutdown affordance.
- Reproduction: start the installed editor and inspect available editor actions/help.
- Evidence: help exposes the `editor` group but no action syntax; release documentation already states explicit interactive shutdown is unsupported.
- Proposed direction: retain as a documented limitation unless installed automation requires a first-class shutdown action.
- Blocks final `v0.1.0`: no.

## Recommendation

`fix-before-v0.1.0`

The deterministic CLI and editor workflows are strong, but the authoritative CLI does not provide sufficient installed command discovery, and two high-severity cwd-dependent runtime/package failures prevent normal consumer-workspace runtime use. Correct and re-dogfood those release-blocking observations before creating the final `v0.1.0` tag. Defer the documentation wording and explicit shutdown affordance if needed.
